#  High-Level Summary of What Happened

* 10 messages entered A’s layer 5.
* B successfully delivered **9 out of 10** messages — this is excellent under 10% loss + 10% corruption.
* The only reason message 10 wasn’t delivered is that the simulation ended immediately after A sent `seq=9` (no time for ack/retransmission).

Nothing in the output indicates a logic bug.

---

#  Walk-Through Explanation (Key Events)

Below is the **simplest possible readable breakdown**, in order.

---

##  **1) A sends `seq=0`, B receives it in-order, ACK is lost**

```
A SEND_DATA seq 0
B RECV_DATA seq 0
B IN_ORDER seq 0 → deliver
B SEND_ACK 0
TO_LAYER3: ack lost
```

✔ B delivered packet 0
✔ But A never receives ACK(0) → A will eventually timeout.

---

##  **2) A sends `seq=1` and `seq=2` before timeout**

```
A SEND_DATA seq 1
A SEND_DATA seq 2
```

Since GBN allows multiple outstanding packets up to window size, this is normal.

---

##  **3) A timeouts → retransmits seq 0,1,2**

```
A TIMEOUT base=0 next=3
A RETX seq 0
A RETX seq 1
A RETX seq 2
```

✔ Correct GBN behavior: retransmit everything in `[base, next)`.

---

##  **4) B receives `seq=1` in-order and delivers it**

```
B RECV_DATA seq 1
B IN_ORDER   seq 1 → deliver
B SEND_ACK   acknum=1
```

BUT note:
A is still expecting an ACK ≥ 0 for seq0, seq1, seq2.

Later…

```
A RECV_CTRL ack=1
A ACK_OK ack=1 base=0 next=3
```

This means:

* ACK(1) acknowledges **packet 0 and 1 and everything before**.
* So A slides `base` → `2`.

---

##  **5) B receives seq=2 and delivers it**

```
B RECV_DATA seq 2
B IN_ORDER seq=2 → deliver
B SEND_ACK 2
```

Then A receives ACK(2):

```
A ACK_OK ack=2 base=2 next=3
A WINDOW_EMPTY
```

✔ All in-flight packets acknowledged → window is empty.

---

##  **6) A sends seq=3 and seq=4 and seq=5**

```
A SEND_DATA seq=3
...
A SEND_DATA seq=4
A SEND_DATA seq=5
```

B receives and delivers seq=3,4,5 except one ACK lost:

```
B deliver 3
ACK(3) lost
B deliver 4
B deliver 5
```

Since ACK(3) was lost, A timeouts again:

```
A TIMEOUT base=3 next=6
A RETX seq3
A RETX seq4
A RETX seq5
```

---

##  **7) ACK(4) and ACK(5) arrive**

```
A RECV_CTRL ack=4
A ACK_OK ack=4 base=3 next=6

A RECV_CTRL ack=5
A ACK_OK ack=5 base=5 next=7
```

✔ Sliding window again as expected.

---

##  **8) A sends seq 6, 7, 8**

Packets 6–8 are delivered in-order:

```
B RECV_DATA seq=6 → deliver
B SEND_ACK 6

B RECV_DATA seq=7 → deliver
B SEND_ACK 7

B RECV_DATA seq=8 → deliver
B SEND_ACK 8
```

B has now delivered **9** packets: seq 0..8.

---

##  **9) A sends seq=9, but simulation ends before ACK comes**

```
A SEND_DATA seq=9
===== SIMULATION ENDS
```

So seq 9 is never delivered, but this is because the simulation runs out of time.

#  Why this output is **correct GBN behavior**

###  GBN requires first in-order seq=0 to be delivered

and it happens.

###  B sends cumulative ACKs

like:

* ACK(1) acknowledges 0 and 1
* ACK(2) acknowledges 0,1,2
* ACK(4) acknowledges 3,4
* ACK(5) acknowledges 3,4,5

Exactly what your log shows.

###  A performs correct timeout → retransmit all outstanding packets.

###  B performs correct out-of-order behavior

For example:

```
B RECV_DATA seq=2
B OUT_OF_ORDER seq=2 expected=3 → resend ACK(2)
```

Correct: B only accepts `expected_seqnum`.
B does **NOT** buffer out-of-order packets in GBN.
